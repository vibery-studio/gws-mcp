# E2E harness: Done 1–10, 16, 21, 22, 24 (local Worker, deployed Worker, or the Docker image)

Drives a running fake-mode gws-mcp and its fake Google as a real MCP client plus browser would. The fake-mode Worker has its own config: the operator's untracked `wrangler.e2e.jsonc` (template `wrangler.e2e.example.jsonc`; production's `wrangler.jsonc` never binds the fake). Locally `npm run dev:e2e`, deployed `gws-mcp-e2e`. Any other `--base` is refused (`target.ts`).

## Local run
```bash
npx tsx scripts/dev-secrets.ts            # once: .dev.vars + fake-google/.dev.vars (mode 600, values never printed)
npm run db:migrate:e2e:local              # local D1 of the E2E config (gws-mcp-e2e)
lsof -i :8787 -i :8788                    # must be free (or held by your own earlier dev servers: stop them)
npm run dev:fake                          # background, port 8788 (fake Google Worker, Durable Object state)
npm run dev:e2e                           # background, port 8787 (E2E config; .dev.vars overrides the URLs; FAKE_GOOGLE via the dev registry)
npx tsx scripts/e2e/run.ts --base http://localhost:8787 --fake http://localhost:8788
```
Stop both dev servers afterwards. Deployed: `--base <PUBLIC_BASE_URL> --fake <FAKE_GOOGLE_PUBLIC_URL> --remote-d1`, both exactly as set in `vars` of the local `wrangler.e2e.jsonc`; without that file (or its `PUBLIC_BASE_URL`) deployed runs are refused.

## Docker run
`bash scripts/e2e/docker.sh` runs the same checks against the Docker image of the Node host (the Dockerfile at the repo root), with the fake Google run locally by `wrangler dev` on 8788 from throwaway secrets. It builds the image, starts `gws-mcp-e2e-app` as the compose file does (read-only root, tmpfs `/tmp`, all capabilities dropped, no-new-privileges, uid 10001, `/data` volume, the token key in a `GWS_SECRETS_FILE` owned by 10001 mode 0400 on a volume at `/run/secrets`), seeds `@fake.test` with the container's `access add`, and runs `run.ts --docker gws-mcp-e2e-app --env-file <throwaway file>`. Around the run it checks `/healthz`, takes a backup with `docker exec` during the run and opens it, restarts the container (`docker-restart.ts`: the sign-in, the AI app's token and the stored Google token survive) and `docker stop` (exit 0, `stopped` logged). Everything it creates is named `gws-mcp-e2e-*` and removed on exit (`E2E_DOCKER_KEEP_IMAGE=1` keeps the image tag).
Needs a running Docker daemon (colima: `colima start`), `openssl`, free ports 8787 and 8788. Port 8787 is the published app port because the fake's default callback is `http://localhost:8787/google/callback`. The container reaches the fake at `host.docker.internal:8788` (colima resolves it to the host; `E2E_DOCKER_FAKE_HOST` overrides the name). Browsers (the harness) use `localhost` for both.
`--docker <container>` makes D1 queries run `node:sqlite` inside that container (`docker exec`), on the server's own database file; only `gws-mcp-e2e-*` names are accepted, the base and fake must be loopback, and `--env-file` must name the throwaway file (the Worker's dev files are never a default there).

`--base`/`--fake` must be `https:`; plain `http:` only for loopback (`localhost`, `127.0.0.1`, `[::1]`), refused before any secret is read or sent.
`--fake` is pinned to the target: a loopback fake for a loopback base, exactly the config's `FAKE_GOOGLE_PUBLIC_URL` for the E2E Worker. Setup then requires the fake's control route to answer 401 without the admin header before any admin or login secret is sent.
D1: `wrangler d1 execute gws-mcp-e2e --local` (loopback) or `--remote` (the E2E Worker), always with `--config` of the E2E config (`scripts/wrangler.ts`; remote needs the local file); never the production database. `--remote-d1` with a loopback base is refused.
Options: `--env-file <path>` (repeatable; default loopback → `.dev.vars`, `fake-google/.dev.vars`; E2E Worker → `.env`), `--only 1,5` (subset, same order).
Secrets read by path: `FAKE_ADMIN_TOKEN` (fake control routes), `FAKE_LOGIN_SECRET` (picker `login_secret`), the target's token key for the Done 9 moved-row test: `TOKEN_ENC_KEY` locally, `E2E_TOKEN_ENC_KEY` for the E2E Worker (the production key is never read). Never in argv or output.

## Before a deployed run
The E2E database needs only its migrations; the harness seeds the rest on every run:
```bash
npm run db:migrate:e2e:remote            # applies 0003 (access list), 0004 (user settings), 0005 (used links) and 0006 (approvals) to gws-mcp-e2e, once per release
```
Setup then allows `@fake.test` as a user (`INSERT OR IGNORE`) before anyone signs in, which also closes the first-sign-in bootstrap, so no real email is ever involved. The E2E database has no admin. Done 22 writes one exact-email admin rule for a made-up address on `allowed.test`, uses it, and deletes it and the rule it added. The E2E Worker and the fake Google must be deployed from the same commit (new fake routes for the marketing services). The saved Ads developer code of Done 21 is a made-up value on a fake account.

## Output
`SETUP ok|FAIL` + lines, then per check `DONE-<n> PASS|FAIL` with evidence lines (`ok …` / `FAIL …` / notes), then `SUMMARY <k>/<n> PASS`. Exit 0 only when all pass. Evidence is run through `src/core/redact.ts` patterns plus every secret the run holds (env secrets, MCP access tokens, cookies).

## Setup (every run, fresh state)
Seeds `e2e-<runId>-a|b|c@fake.test` (preset `default`) via `/__fake/seed`; allows `@fake.test` as a user on the E2E database's access list (`INSERT OR IGNORE`, so a list that already has it is unchanged); signs in as a (first sign-in → connect, lands on Home `/`); connects b through the connect action Google accounts offers (`/connections/connect`, CSRF read from `/accounts`); approves the main client for a only (consent pre-checks nothing, so the harness ticks a).
